### Stream causality

`send_input()` checked only the stream pointer. Video/agent-only sessions therefore
sent `MD_PKT_INPUT` for ordinary viewer mouse/key events. The host's existing
capability check correctly closed the stream. This explains why view-only video
can be stable until local viewer interaction, then repeatedly reconnect. The fix
does **not** ignore unauthorized packets or relax host admission.

Controlled native reproductions, with input disabled and real signed grants:

* **Windows viewer -> Mac host:** interactive-session-1 `WM_MOUSEWHEEL` posted only
  to the W1 viewer at **09:15:29.280802**. Mac host logged rejection of packet
  **0x06** at **09:15:30.461651**; viewer logged connection loss and reconnected.
* **Mac viewer -> Windows host:** a private event producer used public
  `SDL_PushEvent` to queue wheel/key/keyup after decoded video. Queue results
  **1/1/1** logged at **09:25:27.488372**; loss logged at **09:25:27.501531**.
  Windows host logged **packet 0x06 capability/proof violation**. This separate
  **30-second diagnostic is not a ten-minute soak**. The event producer changed
  no production source or system device input; see [SDL's event-queue contract](https://wiki.libsdl.org/SDL2/SDL_PushEvent).
* **Fixed:** repeat Mac queue results **1/1/1** at **09:27:03.590635**, and the same
  owned Windows wheel message at **09:28:18.723310**: **no rejection or loss**.

The committed TCP regression uses an ordered ping sentinel, not an absence sleep:
no grant, video-only, and video+agent must emit no input; video+input still emits
move/button/wheel/key. Counterfactual: **6 failures / 83 checks** before the gate;
fixed: **59 checks PASS**, including the positive granted-input case. Fewer checks
reflect absence of the leaked packets, not removed assertions.

The earlier L7 zero-loss samples do not establish a previous fix. This defect is
reproducible at the assigned base; no causal credit is assigned to old relay
saturation, admission/a11y changes, or codec selection. Removed historical L7 raw
logs cannot prove the cause of every individual historical loss.

## md-n378 teardown diagnosis and regression

Under live bidirectional GUI streams, a predeclared 20-process diagnostic batch
stopped at the **first failure, sample 11**. First ten native exits were 0;
sample 11 printed **all 319 checks passed** but exceeded the unchanged **30s**
guard. LLDB captured this main-thread stack before cleanup:

```
NtWaitForSingleObject -> winpthread pthread_join
 -> libmetadesk nostr_connection_shutdown
 -> ucrt _execute_onexit_table -> libmetadesk _CRT_INIT / DllMainCRTStartup
 -> LdrShutdownProcess -> RtlExitUserProcess -> ExitProcess
```

Only the main and debugger-helper threads remained. The approximately 11 seconds
spent capturing the failed process after the guard were diagnostic overhead,
not a larger test timeout. Windows terminates other threads before DLL detach;
waiting on workers there is unsafe ([ExitProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-exitprocess),
[DLL lifetime guidance](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-best-practices)).

`md_nostr_shutdown()` runs inside the shared module owning the statically linked
nostrc runtime. Host, client and `test_nostr` main wrappers call it after their
normal/alternate-return cleanup, before returning main. This is terminal,
idempotent process shutdown, not ordinary bridge destruction. PE export/import
inspection confirmed the test calls the **DLL's** new API, avoiding a separate
statically linked runtime copy in the executable.

Fixed predeclared batch during the final live streams: **100/100 native exit 0**,
**100/100 stdout files report 319 checks**, **0.171–1.447s** each. No retry past a
failure, timeout increase, assertion weakening, or suppression. The existing
Windows account-persistence subcase remains explicitly skipped.
