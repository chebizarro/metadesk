## Windows snapshot replacement defect

The RC's new quick-hosts reader shares delete, but `MoveFileExW` still cannot
replace a journal held by that reader. A deterministic ARM64 probe compiled
`src/core/win_private.c` directly with `clang -ladvapi32`, held a
`GENERIC_READ` / `FILE_SHARE_READ | FILE_SHARE_DELETE` handle and wrote a new
snapshot: **exit 1**, `replace=0 existing reader=old reopened path=old`.
A writer could therefore report a failed store update while the overlay was
reading the same journal. Simply holding the writer's separate `store.lock`
while reading does not exercise this race.

The Windows managed-store path now flushes the owner-only scratch contents and
uses `FileRenameInfoEx` with [POSIX replacement semantics](https://learn.microsoft.com/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information), keeping the same
owner/DACL, reparse-point and link-count checks. The rename handle requests
write-through and shares read/delete; the existing accounts/credential-store
replacement path is unchanged. The same probe against the fix: **exit 0**,
`replace=1 existing reader=old reopened path=new`. This proves atomic visibility
and old-handle behavior on the VM, not survival of an OS crash or power loss.
The in-suite regression holds the original hosts journal open across a real
`md_managed_store_receive` commit, compares the old handle's bytes, then checks
that a fresh quick-hosts read excludes the removed pin while the first handle
is still open. No timeout, retry or assertion was relaxed.
